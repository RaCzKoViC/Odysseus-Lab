# Odysseus-Lab — analiza projektu i kierunki rozwoju

Data: 2026-09-13 · Stan: `main` @ `a5fe38d` (Lab 0.2.2) · Upstream: Odysseus 1.0.3 (`dev` @ `9d5c031`, 2026-09-11)

Dokument roboczy (nie jest specyfikacją w rozumieniu `specs/_readme.md`). Źródło prawdy o kodzie pozostaje w kodzie i w `specs/`.

## 1. Tożsamość projektu

- **Prywatny, upstream-kompatybilny fork** `odysseus-dev/odysseus` — lokalnego „laboratorium agentów AI" (chat + agent z narzędziami, MCP, pamięć, RAG, e-mail, kalendarz, dokumenty, Cookbook do serwowania modeli). Licencja AGPL-3.0; obowiązki źródłowe pojawiają się dopiero przy udostępnianiu zmodyfikowanej wersji sieciowo innym osobom.
- **Upstream jest duży i szybki**: ~87 tys. gwiazdek, 1182 otwarte issues, 161 otwartych PR, ~69 commitów/miesiąc na `dev`, brak formalnych wydań GitHub. Baza importu = dokładnie bieżący HEAD `dev` (fork nie jest ani przed, ani za upstreamem).
- **Cała historia Lab powstała 2026-09-13**: 45 commitów, 10 PR (9 zmergowanych, #10 otwarty), wykonanych agentami Cursor (`cursor/*-333a`), Codex (dependency catch-up) i Dependabotem. CI na `main` w całości zielone.

## 3. Co zbudowała warstwa Lab (99 plików, +6699/−248)

Kolejność wydań jest prawdziwą sekwencją zależności:

1. **0.1 Foundation** (PR #5) — tożsamość dystrybucji (`/api/version` z lineage upstreamu), `FORK.md` + `UPSTREAM_BASE`, `scripts/odysseus-doctor` (diagnostyka read-only z sanityzacją URL), `scripts/odysseus-compose-backup` (app-data + wolumen Chroma, manifest SHA-256, restore z rollbackiem), `update-lab.sh` / `update_windows.bat` (backup → `pull --ff-only` → rebuild → czekanie na `/api/ready`), `constraints/py311|py314` (pinowanie), utwardzenie CI.
2. **0.2.0 Project Core** (PR #7) — tabela `projects`, ścisły owner-scope, `sessions.project_id` (bez FK, celowo), managed workspace `DATA_DIR/projects/<uuid>/workspace` (symlinki odrzucane, limity głębokości/liczby), pane UI + deep-linki `/projects/{id}`.
3. **0.2.1 Project integrations** (PR #8) — `project_id` w `scheduled_tasks`, `task_runs`, `crew_members` i pamięci JSON; polityki modelu (domyślny endpoint/model projektu) i pamięci (`inherit` / `project_plus_global` / `project_only`); zakładki Agents / Tasks / Models / Memory.
4. **0.2.2 Project operations** (PR #9) — bundle `odysseus-project.v1` (eksport/import bez sekretów, limity 20 MB / 2 MB / 5000 pozycji), `assign` sesji i pamięci, zależności OpenTelemetry w constraints.
5. **0.3.0 Context Engine** (PR #10, otwarty, +1276/−82) — typowane `ContextItem`/`ContextManifest`, 8 stałych kategorii, profile modelu XS/S/M/L, ledger budżetu, `GET /api/session/{id}/context_breakdown`, dostępny Context Inspector. Wyłącznie odczyt; nie zmienia składania promptu.

Edycje hotspotów upstreamu są minimalne (`app.py` +26/−5, `llm_core.py` 2 linie, `chat_processor.py` 16 linii, `memory.py` tryby projektu, `database.py` +132 migracje) — to dobra dyscyplina forka.

- pytest na Windows: **5827 zaliczonych, 115 nieudanych, 23 błędy, 14 pominiętych** w 5 min 53 s (Python 3.12, `PYTHONUTF8=1`). Na Linux CI ten sam zestaw jest zielony; niepowodzenia to klastry zależne od POSIX: testy JS budują `import()` z absolutną ścieżką Windows zamiast URL `file://` (Node 26: `ERR_UNSUPPORTED_ESM_URL_SCHEME`), narzędzia code-nav i confinement zakładają `/tmp`, `~/.ssh` i uprawnienia POSIX (`FileNotFoundError`, chmod/chown w migracji SearXNG), `tests/run_focus.py` zakłada `./venv/bin/python`. Testy warstwy Lab widoczne w skrócie wyniku (Projects, readiness, session owner-scope, upstream-status, update_windows) przeszły. Pełny rejestr niepowodzeń per plik: §8.
- **Znalezisko**: 31 plików testów i 8 plików runtime używa `Path.read_text()` bez `encoding="utf-8"`. Przy locale cp1250 kolekcja testów pada (`UnicodeDecodeError` w `tests/test_document_diff_discard_on_update_js.py`, bajt 0x98). CI Windows uruchamia tylko 4 pliki, więc tego nie widzi. Obejście: `PYTHONUTF8=1`.

## 5. Diagnoza

### Mocne strony

- Bardzo dojrzała baza upstreamu i **kompletne specyfikacje** (`specs/`: 27 subsystemów + 36 providerów) — idealny materiał dla agentów kodujących; każda spec ma sekcję „Current Gaps".
- Warstwa Lab jest **addytywna i izolowana** (nowe pakiety `routes/project/`, `src/project_*`, `static/js/projects.js`), z kontraktem kompatybilności (`FORK.md`), testami i runbookami (`website/operations.md`, `website/upstream.md`).
- Bezpieczeństwo jako pierwszorzędny wymiar: threat model, owner-scope, untrusted-context, SAST/secret-scan w CI, sanitizowane diagnostyki.
- **Projekty** to funkcja, której upstream nie ma (issue upstreamu #220 „Multiple Workspaces" ma 8 reakcji) — realna przewaga forka.

### Ryzyka i długi

1. **Tempo upstreamu vs. fork.** ~70 commitów/mies. i 161 otwartych PR; każda zmiana Lab w `core/database.py`, `routes/memory`, `routes/task`, `routes/session_routes.py` to potencjalny konflikt. Brak automatycznego wykrywania dryfu (`scripts/upstream-status` wymaga ręcznie dodanego remote `upstream`; świeży klon go nie ma).
2. **Projekty są dziś kontenerem metadanych, nie granicą pracy agenta.** Confinement narzędzi działa per-tura przez ręczny wybór folderu (`routes/workspace_routes.py` → `src/tool_execution.py`), a nie przez `project.default_workspace_path`; RAG/dokumenty/skills nie są izolowane per projekt; Files tab tylko do odczytu; zewnętrzne repozytoria niezarejestrowane (spec: „deferred").
3. **Prompt/context bloat dla małych modeli lokalnych** — punkt nr 1 roadmapy upstreamu. PR #10 daje obserwowalność, ale schematy narzędzi/MCP nie są nawet w ledgerze, a chat i agent mają osobne kształtowanie budżetu.
4. **Windows natywny** jest deklarowanym „lekkim" trybem, ale zestaw testów nie jest Windows-clean (encoding), a CI Windows to 4 pliki.
5. Długi upstreamu, które podnoszą koszt każdej synchronizacji: duplikacje `src/` vs `services/` (memory, search, research), `app.py` jako wielki rejestr, heurystyki nazw modeli w `llm_core.py`, frontend bez builda/typów, `style.css` 41k linii.
6. **Brak sandboxa shell/plików** i grube scope tokenów (THREAT_MODEL „known gaps" 1 i 4).
7. Cała historia z jednego dnia, generowana agentami: wysokie tempo, ale brak dowodu użycia Projects w realnej pracy (np. z prawdziwym repozytorium kodu). Ryzyko „dokumentacja wyprzedza użycie".

## 6. Kierunki rozwoju

### Tier A — teraz (2–4 tygodnie): największa dźwignia, mały koszt konfliktu

**A1. Context Engine 0.3.x: od obserwacji do sterowania.** Po merge PR #10: dodać do ledgera rozmiar schematów narzędzi i wyników MCP; stabilne identyfikatory bloków + polityka mutacji (pin / wyklucz / priorytet / blokada kompakcji); profil „slim agent" dla okien 4k–16k (mniejszy domyślny zestaw narzędzi, kompaktowe opisy, retrieval narzędzi zamiast pełnej listy). Miara: tokeny wejścia na turę agenta dla modelu 8B z oknem 8k; odsetek tur bez obcięcia; brak regresji poprawności narzędzi.

**A2. Projekt jako granica wykonania agenta (→ 0.4.0).** Sesja w projekcie ⇒ domyślny workspace agenta = managed workspace lub zarejestrowany zewnętrzny root repozytorium (`get_workspace`/`agent_cwd` z projektu, bez ręcznego wyboru folderu); domyślny model/endpoint projektu stosowany w czacie; następnie izolacja RAG/dokumentów/skills per projekt (kolekcje Chroma z sufiksem projektu). Miara: pełny cykl „otwórz projekt → agent czyta i edytuje repo → zapisuje artefakt do bundla" bez konfiguracji ręcznej.

**A3. Windows-clean.** `PYTHONUTF8=1` w CI i launcherach, poprawka 39 miejsc `read_text()`; pełny pytest na `windows-latest` zamiast 4 plików; smoke `launch-windows.ps1`. Poprawki encodingowe nadają się do upstreamu (mniejszy diff forka).

**A4. Automatyczny raport dryfu upstreamu.** Cotygodniowy workflow: `git fetch upstream`, `scripts/upstream-status --json`, `git merge-tree` dla listy hotspotów, wynik jako issue/komentarz. Reguła: synchronizacja co 2–4 tygodnie w osobnym PR (zgodnie z `website/upstream.md`). Najtańsze ubezpieczenie forka.

### Tier B — następne (1–2 miesiące)

**B1. Sandbox wykonania w obrębie projektu.** Shell i pliki agenta ograniczone do workspace projektu: Linux/Docker — bubblewrap/nsjail lub kontener per projekt z polityką egress; Windows — restricted cwd, deny-lista ścieżek, brak eskalacji. Finer-grained scope tokenów (per-capability) dla integracji Claude Code / Codex. Zamyka dwa z czterech „known gaps" threat modelu i domyka A2.

**B2. Artefakty projektu i zapis w Files.** Artefakty w bundlach, Files tab z zapisem, wersjonowanie `odysseus-project.v1 → v2` z migracją, test round-trip eksport→import (spec gaps).

**B3. Eval harness agenta.** Zestaw zadań end-to-end: fake-LLM (deterministyczny) + realny mały model (Ollama) mierzący poprawność narzędzi, czas do sukcesu, tokeny. `specs/agent-tools.md` wskazuje brak e2e testu `stream_agent_loop`. Bez tego A1 nie da się uczciwie zmierzyć.

### Tier C — strategiczne (kwartał+)

**C1. Odysseus-Lab jako runtime host RacDev Core.** Adapter `racdev_core.runtime`: `ModelAdapter` nad `llm_core`, `ToolDefinition` generowane z `tool_schemas` z uprawnieniami z `tool_security`, `ExecutionContext.project_root` = workspace projektu; Sourceon jako orkiestrator wyżej. Scala trzy repozytoria (kontrakty → lokalny runtime → orkiestracja/research) zamiast trzech osobnych implementacji agenta.

**C2. Kontrybucje do upstreamu** z rzeczy i tak koniecznych (encoding, konsolidacja `src`/`services`, testy route-level). Mniejszy diff forka i wpływ na kierunek upstreamu. Upstream wymaga issue przed PR generowanym agentowo.

**C3. Observability produkcyjna.** OpenTelemetry jest już w constraints: eksport OTLP dla tur agenta (span per narzędzie, tokeny, koszt) i lokalny dashboard; naturalne przedłużenie Context Engine.

### Świadomie nie teraz

- i18n / polski UI — setki stringów w 85 modułach, gigantyczna powierzchnia konfliktu z upstreamem.
- Przebudowa frontendu („Architecture v3", upstream #605) — czekać na upstream.
- Nowe motywy, Postgres jako domyślny, publiczne wydania (repo prywatne).
